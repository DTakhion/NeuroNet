📊 RESUMEN EJECUTIVO
═══════════════════════════════════════════════════════════════════════════════

Objetivo: Mapear transmisión de datos D (cliente) → C (relé) → B (conexión) → 
A (Internet) para diagnosticar problemas de estabilidad entre dispositivos.

Enfoque: Logging estructurado con trace-id UUID + counter incremental.

Resultado: 6 nuevos archivos + 5 archivos modificados = Infraestructura 
completa de diagnóstico lista para uso en desarrollo y testing.

═══════════════════════════════════════════════════════════════════════════════
🔴 PUNTO D: ACEPTACIÓN DE CONEXIONES (DISPOSITIVO)
═══════════════════════════════════════════════════════════════════════════════

📍 Ubicación: server/proxy/manager/TcpProxyManager.kt
   Método: ensureAcceptedConnection()

🎯 Qué hace: Acepta conexiones entrantes del cliente y las registra.

📝 Logs añadidos:
   ✅ "[D-ACCEPT] Conexión entrante aceptada: {address}"
   ✅ logDataFlow('D', "Socket aceptado de cliente...")

🔍 Buscar en logs:
   grep "[D-ACCEPT]" tetherfi_trace.log

📌 Caso de uso:
   - Verificar que el teléfono recibe conexiones del cliente
   - Diagnosticar problemas de puerto bloqueado
   - Validar que se acepta múltiples clientes

═══════════════════════════════════════════════════════════════════════════════
🟠 PUNTO C: RELÉ DE DATOS (PROXY)
═══════════════════════════════════════════════════════════════════════════════

📍 Ubicación: server/proxy/session/tcp/TransportOperations.kt
   Función: relayData() y talk()

🎯 Qué hace: Relaya datos bidireccionales entre cliente e Internet.

📝 Logs añadidos:
   ✅ "[C-RELAY] Iniciando proxy→internet para {address}"
   ✅ "[C-RELAY] Iniciando internet→proxy para {address}"
   ✅ "[C-RELAY] Reporte: proxy→internet={bytes}B, internet→proxy={bytes}B"
   ✅ "[C-RELAY] Sesión finalizada: total {bytes} bytes"

🔍 Buscar en logs:
   grep "[C-RELAY]" tetherfi_trace.log

📌 Indicadores importantes:
   ✅ Relé inicia = Conexión establecida
   ✅ Reportes periódicos = Datos fluyendo
   ❌ Sin reportes = Posible atasco o timeout
   ❌ "Sesión finalizada: 0 bytes" = No pasó datos

═══════════════════════════════════════════════════════════════════════════════
🟡 PUNTO B: BINDING/CONEXIÓN REMOTA (SOCKS)
═══════════════════════════════════════════════════════════════════════════════

📍 Ubicación: server/proxy/session/tcp/socks/BaseSOCKSImplementation.kt
   Método: connect()

🎯 Qué hace: Conecta a destino remoto (ej: 8.8.8.8:443) y relaya datos.

📝 Logs añadidos:
   ✅ "[B-CONNECT] Socket conectado a destino remoto: {address}"
   ✅ "[C-RELAY] Iniciando relayData para conexión SOCKS..."
   ✅ "[C-RELAY] RelayData finalizado para {address}"

🔍 Buscar en logs:
   grep "[B-CONNECT]" tetherfi_trace.log

📌 Caso de uso:
   - Confirmar conexión a servidor remoto funciona
   - Diagnosticar problemas de SOCKS
   - Validar que relay inicia después de conexión

═══════════════════════════════════════════════════════════════════════════════
🟢 PUNTO A: SELECCIÓN DE RED UPSTREAM (INTERNET)
═══════════════════════════════════════════════════════════════════════════════

📍 Ubicación: service/net/AndroidUpstreamNetworkSelector.kt
   Métodos: acquire(), tryAcquire()

🎯 Qué hace: Selecciona WiFi o Celular como salida a Internet.

📝 Logs (ya presentes):
   ✅ "Solicitando red upstream preferida: {WIFI/CELL}"
   ✅ "ÉXITO: Red upstream adquirida..."
   ✅ "ADVERTENCIA: Falla adquisición..."
   ✅ "CRÍTICO: No se pudo obtener conexión..."

🔍 Buscar en logs:
   grep "ÉXITO.*Red\|CRÍTICO\|Solicitando red" tetherfi_trace.log

📌 Diagnosticar:
   ✅ "ÉXITO" = Red disponible y vinculada
   ❌ "CRÍTICO" = Sin conexión a Internet
   ⚠️  "ADVERTENCIA" + fallback = Cambio de red

═══════════════════════════════════════════════════════════════════════════════
🔵 SYNC: SINCRONIZACIÓN DE ESTADO
═══════════════════════════════════════════════════════════════════════════════

📍 Ubicaciones:
   - server/status/BaseStatusBroadcaster.kt (estado interno)
   - app/tile/ProxyTileService.kt (UI/Quick Settings)

🎯 Qué hace: Sincroniza estado entre servicio, UI principal y tile.

📝 Logs añadidos:
   ✅ "[SYNC-STATE] Status transition: {old} → {new}"
   ✅ "[SYNC:TILE] Usuario hizo clic en tile, acción: TOGGLE"
   ✅ "[SYNC:TILE] Servicio está ejecutándose"
   ✅ "[SYNC:TILE] Estado de error: ..."

🔍 Buscar en logs:
   grep "[SYNC" tetherfi_trace.log

📌 Transiciones esperadas:
   1. NotRunning → Running (usuario activó)
   2. Running → Stopping (usuario desactivó)
   3. Running → Error (problema detectado)

🛠️  INFRAESTRUCTURA TÉCNICA
═══════════════════════════════════════════════════════════════════════════════

Nuevo archivo: TraceLoggingManager (core/TraceLogging.kt)

Características:
  🎫 UUID de sesión único
     Formato: TRACE-{UUID}-{COUNTER}
     Permite correlacionar todos los logs de una sesión

  📊 Counter incremental
     Orden cronológico exacto de eventos
     Detecta race conditions y timing issues

  🎚️  Control de verbosidad
     Flag isVerboseLoggingEnabled
     Evita log spam en producción
     Respeta BuildConfig.DEBUG automáticamente

  🎨 Métodos especializados
     logDebug(), logWarn(), logError(), logDataFlow()
     Cada uno con formato consistente

📊 ANÁLISIS POST-CAPTURA
═══════════════════════════════════════════════════════════════════════════════

Después de capturar logs, buscar:

  1. Aceptación (Punto D):
     grep "[D-ACCEPT]" tetherfi_trace.log
     → ¿Aparece? Si NO → problema en puerto/escucha

  2. Relé (Punto C):
     grep "[C-RELAY].*bytes" tetherfi_trace.log
     → ¿Hay bytes > 0? Si NO → datos no fluyen

  3. Conexión (Punto B):
     grep "[B-CONNECT]" tetherfi_trace.log
     → ¿Conecta a destino? Si NO → problema de SOCKS

  4. Red (Punto A):
     grep "ÉXITO.*Red" tetherfi_trace.log
     → ¿Se selecciona red? Si NO → sin Internet

  5. Sincronización (SYNC):
     grep "[SYNC" tetherfi_trace.log
     → ¿Se actualizan estados? Si NO → UI desfasada

⚡ INDICADORES RÁPIDOS DE PROBLEMAS
═══════════════════════════════════════════════════════════════════════════════

❌ PROBLEMA: No acepta conexiones de cliente
   BUSCAR: Falta "[D-ACCEPT]"
   CAUSA: Puerto bloqueado, firewall, o protocolo incorrecto
   SOLUCIÓN: Verificar puerto en build.gradle, permisos Android

❌ PROBLEMA: Datos no fluyen
   BUSCAR: "[C-RELAY] Reporte" con 0 bytes
   CAUSA: Socket cerrado, timeout, o SOCKS rechaza comando
   SOLUCIÓN: Revisar logs de SOCKS en BaseSOCKSImplementation

❌ PROBLEMA: Desconexiones frecuentes
   BUSCAR: Múltiples "[D-ACCEPT]" en corto tiempo
   CAUSA: Timeout, buffer overflow, o red inestable
   SOLUCIÓN: Aumentar timeouts en ExpertPreferences

❌ PROBLEMA: UI/tile no actualiza
   BUSCAR: Falta "[SYNC-STATE]" o "[SYNC:TILE]"
   CAUSA: ServiceRunner no notifica cambios
   SOLUCIÓN: Verificar inyección de StateFlow
